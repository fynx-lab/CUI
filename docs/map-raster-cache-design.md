# Map tile raster cache — implementation design (approved in conversation)

Goal: preserve full map detail while panning loaded tiles; avoid rebuilding road/water geometry each frame. Keep the C99 core provider-neutral and Vivida untouched.

- Add an optional host-supplied raster lookup to `cui_map_opts`. The map still gets decoded tiles via `lookup` for label placement; if the host also supplies a texture, it paints that tile's base image instead of regenerating its base geometry. Labels and markers are drawn above all tiles for cross-tile collision and interaction. Without a texture the existing vector path works unchanged. This is not MapLibre styling.
- Expose the same base-geometry painter as a small C99 public helper for hosts to draw a decoded 256×256 tile into an offscreen context. Offscreen rendering and caching are in the Windows C++ demo, never the widget's network/cache policy. Use a separate software context/renderer for the offscreen picture; upload resulting RGBA to the demo's UI renderer on the UI thread.
- Demo cache: key by z/x/y and the demo's fixed dark theme plus DPI; 48 MiB max for raster textures in addition to the 96 MiB decoded-tile cache, evict LRU textures not used in the preceding frame. No raster cache eviction while a frame still references the texture. When tiles unload, discard raster textures; on DPI change invalidate and rebuild. Hosts with mutable themes must also invalidate on theme change. First-load work is capped at one tile per UI frame; uncached tiles use vector fallback.
- On drag, retain the complete painted base image (no temporary road/park filtering for raster-backed tiles), with labels/markers remaining dynamic. Missing tiles still show placeholders and are only requested for the viewport and border.
- On Windows, load an existing installed Chinese-capable font for body fallback where available; do not bundle a restricted OS font or invent labels from external data. Otherwise leave available tile text and document unsupported glyph fallback.
- Verify: deterministic vector-vs-raster rendered pixels at 1× and 2× DPI, raster-eviction eligibility tests, live Beijing z7 screenshot (Chinese labels) and synthetic 100-frame drag A/B timing (`cui_app_frame` around render/presentation, not standalone per-stage timing). Cache stayed at 3.8 MiB in the sampled viewport; 48 MiB is a cap, not measured steady-state usage. Separate input, geometry, software raster and presentation timings and real-mouse latency remain future work; do not claim an interactive FPS result from the synthetic probe.

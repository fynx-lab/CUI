# Detailed vector-map labels at z13–14

## Goal and evidence

The current C99 widget renders names only from the `place` MVT layer; it already paints base roads and water at z14, but not street, POI or landmark names. Read-only inspection of already cached OpenFreeMap z13/z14 tiles confirmed `transportation_name`, `poi`, `water_name`, `waterway`, `park` and `mountain_peak` layers. Some z14 tiles contain over 1,900 POI features. Make these named layers eligible at zoom **13 and above** while keeping z0–12's existing place-only labeling. This is not a full MapLibre style engine, and does not imply every name can be legibly drawn at once.

## Decoder and data safety

Extend the existing bounded MVT parser to retain name, class and relevant geometry from recognized point (`poi`, `water_name`, `mountain_peak`), line (`transportation_name`, existing `waterway`) and polygon (`park`, when named) features. Parse only the tile-provided `name` (no remote fonts or glyph service); unrecognized layers remain ignored. Geometry anchors: point coordinate for points; midpoint of a suitable long segment for lines; a bounded representative position for a named polygon. Do not rasterize text into base tiles. Existing 2 MiB uncompressed input bound, 16,384 keys/features per recognized layer, 32,768 values, 12,000 retained features and bounded point/path allocations remain in force. Bound retained candidates per tile: at most 2,048 POI, 512 road names, 256 water names, 128 park names and 128 mountain-peak names; names on the already decoded `waterway` geometry contribute at most 256 label candidates without limiting waterway rendering. If an optional candidate cap fills, ignore further candidates in that optional layer without rejecting an otherwise drawable base tile; still bound and validate the layer's protobuf framing. If an optional layer exceeds the existing key/value/feature table caps, skip that optional layer instead of rejecting unrelated base geometry. Malformed geometry for a candidate admitted within the cap remains an error. The global 12,000 retained-feature/point/path bounds remain mandatory.

## Label selection and presentation

Markers reserve collision space first. At z13–14: select place names before transportation names, then named water/landmarks, then POI; names in each category use deterministic tile/feature order and world-anchored cells, not random frame-by-frame sampling. Allow up to **256 total labels** and at most **three accepted names per 192-map-pixel world cell** at z13–14; z0–12 retain 192 total and two per cell. Check global label collision and viewport clipping for every candidate. Text stays horizontal for this first increment, including roads (no line-following shaping), and keeps the CUI theme-aware `place_text` palette color. Place/POI markers and names remain live over rendered raster tiles. When decoded geometry is evicted but a raster image remains, tile-provided names may be temporarily absent until data is available again; they are never baked into the image.

## Boundaries and verification

Do not change transport, TileJSON, cached source namespaces, 192 MiB decoded/96 MiB raster budgets, z0–14 service range, current road visibility rules, or attribution. Cover named point/line/polygon fixtures, z12 versus z13 cutoff, precedence/collision, stable panning, oversized optional label candidate handling, and UTF-8/CJK fallback in offline test sources. Compile without running tests or opening a window by default, per user instruction. Real-world z13/z14 visual density and drag performance need user-approved visual verification; stage timing logs should distinguish label painting from software rasterization before any performance claim. Keep local commits unpushed.
